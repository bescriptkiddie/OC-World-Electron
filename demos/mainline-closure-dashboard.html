Product

产品

已经完成

  • 聊天后刚写入的关系和历史，会影响下一轮回复，不再滞后。
  • 手动触发 recall 时，不会继续拿旧快照做提示判断。
  • prompt 开始基于当前语境提取相关记忆、相关项目、相关事项，不再把整包 retrieval 直接挂在 snapshot 上。
  • recall hint 现在会顺带带出相关记忆和相关事项，更像可用的轻提醒。
  • task / project 的生成开始更克制，不再只要沾上关键词就粗暴落项目。
  • Hermes 在主线里只暴露 bridge 契约，没有伪装成“已经全接通工具 runtime”。

还要调整

  • 记忆、project、recall 的多用户持久化边界还没彻底统一。
  • UI 还看不到真实 Hermes session 事件流，只能看到 status 和契约壳。

影响面

用户现在不只是看到“重复信号”，而是能更快理解这个提醒和哪段长期记忆、哪个推进事项有关；同时事项列表也更不容易被弱意图和脏标题污染。

Architecture

架构

已经完成

  • Hermes 边界：主线已明确成 bridge contract，不把 OC 伪装成 agent runtime。
  • ContextSnapshot：从“每次都重拼”收成“可缓存、可显式失效”的主链状态入口。
  • Recall：手动评估站到“读新快照”这一边，提示文本也开始接 long-term memory / work-item 上下文。
  • Memory Retrieval：从 snapshot 中拆出，变成按 querySignals 取相关内容的独立层。
  • Work / Project 聚合：开始从“粗关键词触发”收成“强意图 + 规范化标题聚合”。

还要调整

  • 统一记忆仓：主线还挂着 `unified-memory.ts` 旧形态，需要收口到更清晰的 user-scoped 边界。
  • 事件流：`onSessionEvent` 只是订阅壳，main → renderer 的真实 Hermes 事件转发没接。

影响面

这轮让 recall 与 work-item / project 聚合都开始吃更像“真实产品状态”的上下文，而不只是最低限度的数据结构拼接，后面更容易继续拔掉旧链路的粗糙默认行为。
